# DEV_PATH_V03 v4 amendment — 2026-08-28

This amendment exists to make the 2026-08-28 Gate 0 and extraction decisions machine-reviewable without silently rewriting historical v2/v3 planning text. Where this file conflicts with older wording in `DEV_PATH_V03.md`, this amendment is authoritative until the next consolidated DEV_PATH revision.

## Gate 0 authority

- `make ci` is a developer / potentially degraded loop. If z3 is absent, it must print `DEGRADED` and MUST NOT be cited as authoritative green evidence.
- `make ci-full` is the local Gate 0-b authority. It requires the `formal` extra, z3 availability, and at least one actually executed SMT test; all-SMT-skipped is a hard failure.
- `make clean-ci` proves reproducibility from the committed project plus its root registry authority: committed `HEAD:.` tree + `HEAD:registry.yaml` → fresh repository layout and venv → install `.[research,dev,formal]` → `make ci-full`.
- `make baseline` is the G0-c producer. It writes a dated baseline only after both current-checkout `ci-full` and clean archive `clean-ci` pass, and records unit-test/skip counts, SMT discovered/executed/skipped counts, dependency versions, and content hashes for acceptance/certificate artifacts.
- A large milestone does not exit Gate 0 without a committed baseline generated by that procedure.

## W3-0 explicit deferral decision

**W3-0 MathArc Engine extraction is deferred from v0.3-core to the v0.4 entry point, and it does not start until a second real consumer exists.**

Rationale: F0.5 `RouteEvaluationRecord`, F2 promotion semantics, R5 three-channel failure semantics, and their evidence/assurance boundaries are still being stabilized. Extracting the engine before these contracts settle would turn v0.2/v0.3 implementation accidents into reusable APIs.

A valid second consumer is a real non-Research caller (for example a Resolve/EDA path) or another concrete project. A slide, future plan, or expected reuse does not count.

Migration-cost risk does grow as `matharc/v02` grows. That risk is owned by the **Harness_Engineering repository owner** and must be re-reviewed at every v0.3 milestone close. The milestone PR/G0-c baseline records one of two decisions: `DEFER_W3_0` with the current reason, or `START_W3_0` with the named second consumer. Rising move cost is not by itself permission to generalize an unstable interface early.

## Prototype freeze

`docs/prototypes/review-console.html` is the current **v3 recruiting/demo prototype** and is frozen as `FROZEN_RECRUITING_DEMO`.

No additional visual/product iteration should be funded before all of the following are true in the authoritative gate:

1. F0.5 negative semantics are locked: `property_random` no-counterexample ⇒ `INCONCLUSIVE`, never `PASS_BOUNDED`.
2. F2 negative gate is locked: a structured active route without a current qualifying evaluation cannot promote a claim.
3. R5 negative semantics are locked: review gap changes no theorem status; route failure changes only the route; only an independently verified claim counterexample may trigger claim refutation/cascade.
4. `make ci-full` passes on the current committed tree.

Exceptions are limited to security, privacy/data-leak, or accessibility blockers. Recruiting may continue using the frozen prototype; the prototype is not evidence that its backend contracts exist.

## Real Claude Code smoke evidence

Historical prose that a real Claude Code CLI turn was executed is a non-authoritative observation unless the run has a versioned artifact.

The reproducible entrypoint is now:

```bash
make smoke-claude
```

It uses synthetic mathematical input and writes a sanitized artifact containing structured proposal output, public trace, ToolCallRecord and ModelUsage. Raw prompt/stdout are intentionally excluded. A current-end-to-end claim is allowed only when that artifact (or its content hash in the milestone baseline) is present.

## Count drift policy

Do not hand-maintain a current `mypy` source-file count or unit-test count in planning prose. The audit-time correction from 39 to 40 was valid for that historical snapshot, but v0.3 subsequently added more modules. `make baseline` dynamically records the current `matharc/v02/**/*.py` count and test/skip counts; the dated baseline is the SSOT.

## Branch hygiene

Repository-wide governance changes (`HARNESS-LAYERING.md`, global `registry.yaml` policy, `AGENTS.md` placement rules) should use a dedicated `governance/*` or narrowly scoped governance-fix branch. MathArc research feature branches should not carry unrelated governance commits. This amendment/fix is intentionally on `fix/matharc-gate0-ci-evidence`, separate from the merged v0.3 feature PR.
